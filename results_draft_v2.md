## 5.1 Synthetic CBF validation (pre-registered head-on scene)

The sanity-check scene of Protocol §4.2 places a single low-safety hazard on the straight-line path between start and goal, assigns all other geometry a near-safe background score, and drives each mode through the harness's Phase-A path, in which the safety field is overridden by a synthetic hazard so it is known exactly by construction. Two things are reported: an implementation-correctness check of the barrier geometry, and the NONE-versus-ALPHA_SCALE control-response comparison the scene exists to exercise.

Two implementation-correctness checks passed first. The collision-cone barrier value for a robot heading straight at the synthetic obstacle matched an independent hand computation exactly, `h = β·γ − δ² = −119.456`, confirming that the existence condition and barrier (Eq 9a/9b, Eq 13) were transcribed correctly; and a receding trajectory was confirmed not to activate the constraint. These establish that the geometric primitive is implemented faithfully before any semantic weighting is layered on.

**Scene provenance.** The original synthetic scene from which an earlier, larger ALPHA_SCALE slowdown was reported was never written to disk and is confirmed absent from every machine used in this work; it cannot be re-run, and its earlier numbers are superseded here rather than carried forward (Flag 1). A first reconstruction attempt — an isolated hazard of inflated radius r_phys ≈ 0.50 m, offset 0.03 m from the path — proved too mild to exercise the intended regime: with effectively unbounded lateral space, both NONE and ALPHA_SCALE cleared it at full speed (time ratio 1.06 each, path-length ratio ≈ 1.00). That is a genuine observation about how sensitive the encounter is to hazard geometry, not a usable sanity-check result. The reported result therefore comes from a scene whose geometry was fixed by a criterion set in advance and derived from robot and splat geometry alone, with no outcome-driven tuning of hazard size, placement, or collar radius. The criterion has two parts. **Blocking:** the hazard's Minkowski-inflated boundary must cover the direct start→goal path — with hazard isotropic scale s_h = 0.10 and robot radius ρ = 0.16 m, r_phys_hazard = c_base·s_h + ρ = 0.4968 m, while the path passes only 0.030 m from the hazard center, so a straight run penetrates the inflated boundary by 0.4668 m. **Narrow clearance:** the robot-center lateral corridor between the hazard's inflated boundary and the clutter collar's inner inflated boundary is set to half the robot footprint radius, W_center = ρ/2 = 0.080 m, a free band narrower than the robot itself, from which the collar radius is *solved* rather than chosen: R_collar = W_center + c_base·(s_h + s_c) + 2ρ = 0.8715 m. Here c_base = √χ²₍₃,₀.₉₉₎ = 3.36821 and s_c = 0.04. The scene (`scenes/prereg_headon.py`, seed 42, committed in `8caa5ba`) was generated once and evaluated once, under both QP backends.

**Result.** On this scene the two modes are deterministically distinct, and the difference runs opposite to the design prediction.

**Table 1 — pre-registered head-on scene, seed 42, default kₐ_base = 1.0.** Severity is the shared true-geometry signed distance in Mahalanobis units (more negative = deeper inside the true confidence ellipsoid); both modes are graded against the same boundary.

| mode | reached goal | path-length ratio | time ratio | severity | near-miss | infeasible |
|---|---|---|---|---|---|---|
| NONE | yes | 1.0003 | 1.1418 | −0.1330 | 1 | 0 |
| ALPHA_SCALE | yes | 0.9999 | 1.0597 | −0.4251 | 1 | 0 |
| COV_INFLATE (λ = 1.0) | **no** | 0.4416 | 14.9254 | +0.7573 | 0 | 0 |

The two modes take the *same path* — path-length ratios 1.0003 (NONE) and 0.9999 (ALPHA_SCALE), within 4×10⁻⁴ of each other and of unity, so neither departs laterally. ALPHA_SCALE completes **faster**, not slower: time ratio 1.0597 against NONE's 1.1418. And ALPHA_SCALE has **worse** collision severity, −0.4251 against NONE's −0.1330. Both backends reproduce this identically — |Δtime_ratio| = 0.00×10⁰ and |Δpath_length_ratio| ≤ 9.54×10⁻⁸ for both modes — so it is confirmed not to be a solver artifact. This directly contradicts and supersedes the earlier characterization of ALPHA_SCALE as producing the "same path, slower approach," which came from the unpersisted scene and turned out to be wrong; faster-and-deeper is the opposite of that, and the opposite of the design intent that a lower safety score should brake harder along the approach axis. The pre-registered criterion did its job only in part: it predicted that a corridor narrower than the robot's own radius would force a real deceleration or a real lateral departure, and NONE did decelerate (1.1418) without departing laterally, but ALPHA_SCALE did neither — it went through. The scene is materially harder than the too-mild first attempt and it does separate the modes, just not in the predicted direction.

**Mechanism investigation.** A per-step constraint-activation trace was run on this scene to test the obvious explanation — that at the steps where ALPHA_SCALE's severity is worst, the hazard's own barrier is the dominant active constraint and the smaller gain shrinks the required correction there. That hypothesis is refuted in its specific form. The collision cone's activation gate, `cone_exists = (h ≤ 0) ∧ (δ ≥ 0)`, contains no kₐ term, and `A` and `s_min` are byte-identical between the two modes, so the active set at a given state is mode-independent by construction; empirically both modes first activate at step 13 from a bit-identical state. Because δ = rᵀAv flips negative as the robot passes the hazard, the barrier releases while the robot is still inside the inflated ellipsoid — NONE's hazard constraint is active over steps 13–54 and releases at step 55, ALPHA_SCALE's over steps 13–49 releasing at step 50 — and each mode's deepest penetration then occurs on the very next step, with the hazard constraint **not active**; ALPHA_SCALE's active set at that step is empty. There is therefore no dominant active constraint at the worst step for a gain to act on. A matched-state test at step 13, where the trajectories are still identical and kₐ is the only variable, does confirm the second half of the hypothesis: with h = −1039.0605, the required correction ‖u_safe − u_ref‖ falls from 1.276847 at kₐ = 1.0 to 0.994977 at kₐ = 0.1. But the reduction is strongly sublinear and bounded below — a 1000× gain reduction buys only 24.5% — and the floor is derived analytically rather than fitted: as kₐ → 0 the constraint tends to wᵀu ≥ 0, whose distance from u_ref is −w·u_ref/‖w‖ = 0.963659, against a measured 0.963972 at kₐ = 10⁻³. kₐ scales the constraint *offset*; it cannot rotate the constraint *direction*, and the direction is what sets the floor. Over the active window the hazard does dominate (ALPHA_SCALE 37/37 constrained steps, NONE 30/43), and essentially the entire severity gap is already present at the moment the barrier releases (−0.1186 vs −0.4164, against final −0.1330 vs −0.4251), so whatever produces it accrues across the window rather than at a single binding step. Whether the per-step reduction accumulates across that window into the full −0.29 severity gap is **consistent with the data but not established** — no counterfactual has been run, and this is stated here as an open question, not a conclusion.

**COV_INFLATE on this scene.** At λ = 1.0, COV_INFLATE does not reach the goal under either backend. Its time ratio of 14.9254 is the `max_steps` ceiling (2000 steps × 0.05 s = 100 s against a 6.70 s oracle), so it exhausted the step budget partway along the corridor rather than converging slowly, with `infeasible_count` = 0 — the QP never reported infeasibility or took the max-braking branch, consistent with §5.2's gain-artifact finding. Its severity is the best of the three (+0.7573): it stays well clear, and never arrives. Whether the W_center = ρ/2 corridor is simply too tight for λ = 1.0 inflation was not tested here; no gain or λ sweep was run on this scene. Unlike NONE and ALPHA_SCALE, this row is *not* backend-agreeing — path-length ratio differs by 1.17×10⁻² and severity reads 0.7573 under Clarabel against 0.8961 under SLSQP, roughly an 18% spread — so it is the least trustworthy row in the table and should not be quoted without that caveat. Both backends do agree that it fails to reach the goal and that it hits the same step ceiling.

## 5.2 COV_INFLATE disambiguation and gain sweep

COV_INFLATE's behavior required a dedicated disambiguation, and the arc of that investigation — including a magnitude correction that arrived later than the original measurement — is reported here in full rather than as a single settled number.

**The original finding and its correction.** On the reconstructed narrow-corridor synthetic scene (a seeded generator standing in for the original sanity-check scene, which had never been persisted to disk), COV_INFLATE at λ = 1.0 reached the goal but did so with an ~11.9× slowdown relative to the oracle time-to-goal (time ratio 11.91), while its path length was essentially unchanged from NONE — i.e. it crawled rather than rerouted. That 11.91× figure was measured under the then-default SLSQP QP backend. The solver-verification work reported in §5.3 subsequently established that roughly half of that slowdown was SLSQP suboptimality rather than the semantic-weighting mechanism: under the now-default Clarabel backend, the identical scene and configuration give a **5.90× slowdown (time ratio 5.8955)**. The corrected figure is therefore ~5.9×, not ~11.9×. The qualitative finding below is unchanged by this correction — every supporting leg of it was verified bit-identical across the two solvers (§5.3) — but the magnitude of the headline slowdown was overstated by a factor of roughly two, and 5.9× is the number to quote.

**The corridor is passable — this is not a no-safe-corridor refusal.** Three independent lines of evidence rule out the interpretation that COV_INFLATE at λ = 1.0 was correctly refusing an impassable corridor:

1. *Infeasibility check.* Across the narrow-corridor runs at the default gain, the QP never once fell back to its max-braking branch: `infeasible_count = 0` on every mode and every λ, including the pathological λ = 1.0 run. A direct trace of that run showed the barrier value `min_h` was negative on 96% of steps, yet the solver reported `success = True` at every single step — it always found a feasible control and simply chose a near-zero net acceleration (73% of the 1596-step trajectory was spent below 1 cm/s). This rules out QP-infeasibility / fallback-to-max-braking as the cause of the slowdown at the default gain `kₐ_base = 1.0`.

2. *Wide corridor.* Holding λ = 1.0 and `kₐ_base` = 1.0 fixed and changing only the surrounding geometry — widening the corridor's baseline clearance from ≈10.8 cm to ≈50.8 cm — collapses the slowdown to a time ratio of **1.09×**, essentially indistinguishable from NONE, while achieving an even better safety margin (severity +1.190 against +0.165 on the narrow corridor). Same weighting, same gain, only the geometry loosened, and the pathology vanishes.

3. *Gain sweep.* Sweeping `kₐ_base` across two orders of magnitude on the narrow corridor, with λ = 1.0 fixed, is non-monotonic and shows the slowdown is governed by the gain, not the geometry (Table 2). At *lower* gains the corridor is traversed briskly (1.18× at 0.1, 1.25× at 0.3); at the default gain the crawl appears (5.90×); and at *higher* gains the QP does eventually go genuinely infeasible — `infeasible_count` rises to 2 at `kₐ_base` = 3.0 and 40 at 10.0, and the robot fails to reach the goal within the step budget in both cases. Real QP infeasibility therefore exists, but only at gains well above the default, as a further consequence of pushing the same gain mechanism harder — not as the explanation of the original default-gain finding.

**Table 2 — narrow corridor, λ = 1.0, `kₐ_base` sweep.** Time ratios and infeasibility counts; `kₐ_base` = 1.0 is the Clarabel-backend value (see §5.3), all other rows are bit-identical across both backends.

| `kₐ_base` | reached goal | time ratio | infeasible_count |
|---|---|---|---|
| 0.1 | yes | 1.18 | 0 |
| 0.3 | yes | 1.25 | 0 |
| 1.0 | yes | 5.90 | 0 |
| 3.0 | no (timeout) | — | 2 |
| 10.0 | no (timeout) | — | 40 |

The same corridor that is trivially passable at `kₐ_base` 0.1 and 0.3 (~1.2×) and at any tested λ once widened (~1.1×) is navigated far more conservatively at the default gain: narrow-at-default (5.90×) is still roughly 5.4× slower than wide-at-default (1.09×). The conclusion, stated precisely: the COV_INFLATE near-halt at the default gain is a **fixed-gain artifact of `kₐ_base`, confirmed — not a legitimate no-safe-corridor refusal, and not QP infeasibility at the default gain.** The whole of Steps 0–3 was independently re-run from scratch on 2026-07-12 from the committed seed-42 generator and reproduced to every displayed digit, including a cross-check against the stock CLI, so both the mechanism and the literal numbers are reproducible for this scene. All of it remains a single-scene synthetic finding; what it establishes is a property of the implementation's behavior on a controlled scene, not a real-navigation result.

## 5.3 Solver verification

Protocol §4.4 deliberately deferred a set of numbers to Results — the outcome of the two-backend state-by-state re-solve. Those numbers are reported here. This began as independent verification of solver correctness and happened to surface the correction to §5.2's magnitude; it is reported as what it is, a real correction to a previously recorded result, not a footnote.

The QP is solvable by two independent backends: Clarabel (interior-point conic, handling the actuator bound ‖u‖ ≤ a_max as a native second-order cone) and SLSQP (sequential least-squares, retained as a fallback). Because the two implement the same constraints by entirely different algorithms, every QP sub-problem along the narrow-corridor `kₐ_base` = 1.0 rollout was re-solved with both backends and their objective values and constraint satisfaction compared at identical states (1478 both-feasible steps).

The two backends agree on the coarse outcomes everywhere. `reached_goal` and `infeasible_count` are identical across the entire gain sweep — including the `PrimalInfeasible` counts landing on exactly SLSQP's 2 and 40 at `kₐ_base` 3.0 and 10.0 — and every metric at the wide corridor and at gains 0.1 and 0.3 is bit-identical. Two unrelated algorithms declaring infeasibility on precisely the same steps is strong evidence that the conic reformulation is faithful. The entire divergence between the backends is the single default-gain narrow-corridor point.

At that point, the state-by-state objective comparison identifies which backend is correct. Clarabel never exceeds SLSQP's objective by more than float noise (at most ~3.8×10⁻⁸). In the other direction, SLSQP's objective exceeds Clarabel's by as much as 7.6×10⁻² — roughly 7% of the ≈1.02 mean objective — on about 12% of the constrained steps, while every one of those solves still reported `success = True`. Both backends respect the actuator bound (max ‖u‖ ≈ 0.9998 against the bound of 1.0) and both carry the same small worst-case CBF slack (−9.3×10⁻⁴), so neither is buying a lower objective by violating a constraint. SLSQP was therefore returning suboptimal — over-conservative — controls on a minority of constrained steps while reporting success.

The suboptimality is self-reinforcing. Driving the same rollout with Clarabel and re-solving each state with SLSQP, the two agree to 1.6×10⁻⁹: SLSQP's error is state-dependent and appears only on the harder states that its own earlier over-conservative controls steer the trajectory into. A defect on ~12% of steps that specifically compounds on the states it creates is why a per-step suboptimality inflates into roughly a 2× traversal-time difference — the 11.91× versus 5.90× gap of §5.2. On the strength of this comparison the default backend was set to Clarabel, with SLSQP retained as a still-tested fallback; the ~5.9× COV_INFLATE figure quoted in §5.2 is the Clarabel value.

Two details of the comparison are worth recording because they bear on how much weight it carries. Only two solver statuses were ever observed across every rollout — `Solved` and `PrimalInfeasible` — so the deliberately strict status mapping (anything other than `Solved` routes to the max-braking fallback) never had to adjudicate a reduced-tolerance `AlmostSolved` case; that is a measured non-issue on these scenes, not a settled principle. And the two backends' reported objective values are not directly comparable in absolute terms: Clarabel minimizes ‖u − u_ref‖² where SLSQP minimizes ½‖u − u_ref‖², the same argmin at twice the reported value, which the comparison above accounts for.

## 5.4 VLM safety-score consistency

The VLM consistency protocol (§4.6) — repeated queries of the production safety-auditor prompt against a fixed object set, measuring the within-object spread of the returned [0,1] scalar — was run in two passes. Both are reported, and the second does not confirm the first.

**Pass 1 — stock-photo object set (2026-07-09).** Ten stock object images spanning an intended safety gradient (wall, heavy bookshelf, cushion, yoga mat, wooden chair, potted plant, vase, glass, cable, knife), five queries each at temperature 0.2. Within-object variance was zero for 9 of the 10 objects. The sole unstable object was the plain wall — intended as the most obviously-safe baseline — which flipped bimodally between exactly 0.0 and 1.0 across its five queries (mean 0.4, standard deviation 0.55). This was the opposite of the expected pattern: intuitively ambiguous objects such as the wooden chair and potted plant were perfectly stable, while the "easy" wall was the one that swung. The finding was hypothesized to arise from the prompt's "flat solid ground" safety anchor making a vertical wall categorically ambiguous.

**Pass 2 — real Replica room0 frames (2026-07-18).** The identical methodology was re-run against ten objects rough-cropped by hand from real Replica `room0` RGB frames, under the current production model pin `gemini-3.5-flash`, temperature 0.2, five queries each; all 50 calls succeeded on the first attempt. The object set deliberately included a carpet-floor patch added as the "flat solid ground" positive control that the Pass-1 hypothesis specifically calls for. The overall shape of Pass 1 replicated — 8 of 10 objects were perfectly stable (Table 3) — but the specific wall finding did not, and did so in a way that falsifies the Pass-1 explanation rather than merely failing to reproduce it:

- The wall, the single unstable object in Pass 1, was here the *most* confidently stable object in the run: 1.000 across all five queries, standard deviation 0.000.
- The floor control — the cleanest possible test of the "ground-anchored language" hypothesis — was also completely stable (0.950, standard deviation 0.000). Because the hypothesis predicts the floor should be the *most* susceptible to the "flat solid ground" anchor, its perfect stability falsifies that specific explanation as a general mechanism, rather than just leaving it unreproduced.
- Instability instead appeared on two different, previously rock-solid categories — a tufted ottoman (standard deviation 0.022) and an upholstered accent chair (standard deviation 0.045) — and at roughly an order of magnitude smaller scale than the Pass-1 wall: single-query jitter of about ±0.05 within a tight cluster, not a full swing between the scale's two endpoints. No object in Pass 2 reproduced wall-like bimodal instability.

The migration of the (much smaller) instability to two new objects is not yet established as a real pattern as opposed to ordinary run-to-run sampling noise at temperature 0.2; distinguishing the two would require re-testing at a higher temperature, and Pass 1's own temperature-0.2-suppresses-variance caveat applies to Pass 2 unchanged.

One scale-calibration observation is consistent across both passes rather than in tension between them: non-drivable solid furniture scores near zero regardless of how heavy or stable it actually is — the credenza and the wood side table both 0.000 in Pass 2, matching Pass 1's heavy bookshelf at 0.000 — because the prompt's 1.0 anchor is "flat solid ground," not "stable object." This is a property of the prompt's scale, not an instability.

## 5.5 What has not yet been evaluated

To be explicit, and not to leave this buried: no real Phase B result exists. Stage 3 has only ever been run against synthetic scenes (§5.1–§5.3) and the VLM consistency check has only ever been run on hand-cropped images (§5.4); neither has ever been run against a real `safety_gsplat.ply`, because no real `gsplat.ply`, `params.npz`, `classifier.pth`, or `safety_gsplat.ply` has been confirmed to exist on any machine used in this work — an explicit negative result from a repo-wide and machine-wide search, not an assumption. The real-data three-mode comparison of Protocol §4.5 — the only test of whether semantic weighting changes navigation outcomes on real, non-synthetic hazards — is blocked on a real Stage 1/2 output and on lab/GPU access, and produces no result here.

Three further limits belong in the same paragraph rather than in a footnote. The corrected Stage 2 classifier loader has never been run against real trained weights, since no `classifier.pth` exists to run it against; its correctness is established by code inspection and a state-dict round-trip test, not by a live decode. The spatial prefilter's radius, candidate cap, and opacity-prune threshold are still placeholder values that have never been measured against the real `room0` scene's bounding box. And the robot footprint radius ρ = 0.16 m, which sets every Minkowski inflation in §5.1, is a placeholder that has not been confirmed against the actual TurtleBot4 platform.
